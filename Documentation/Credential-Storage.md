# Credential access and update prompts

## Current behavior

Yap reads and writes only its consolidated Keychain item, `app.yap.credentials` / `personal-connections-v1`. Records are cached within the process and saved atomically. Disconnecting removes the active connection record; switching Zoom configuration removes its related records together and preserves Google credentials. A failed vault write is reported and cannot replace the cached or stored credentials.

Packaged builds get the Google desktop client ID and secret from their signed bundle. These public desktop-client credentials identify Yap; user access and refresh tokens stay in Keychain. There is no credential import step in packaged builds. See [Google Calendar](GoogleCalendar.md).

The app no longer imports or deletes credentials from older app names or separate pre-consolidation Keychain items. This removes legacy access prompts and cleanup errors. An installation that only has old credentials must sign in again. Existing records already in Yap's consolidated vault remain usable. Keychain protection, signing requirements, and normal macOS prompts remain in effect.

Tests cover cached reads, absence of legacy reads/deletions, failed reads and writes, atomic disconnect, preservation of the other account, concurrent saves, and rejection of malformed active vault data.

## One secure item and one process cache

`YapCredentials.CredentialVault` consolidates the four records into one non-synchronizing generic-password item, `app.yap.credentials` / `personal-connections-v1`, accessible only while the device Keychain is unlocked. Active records use `app.yap.personal.configuration` / `google-desktop`, `app.yap.google-calendar` / `personal`, and `app.yap.zoom-personal` / `configuration` or `oauth-tokens`. The shared vault serializes reads and updates across the calendar and Zoom actors, and caches successful reads for the running process. Ordinary view/status refreshes use that cache.

When the Yap vault is absent, the explicit legacy `app.whoosh.credentials` vault is read through its existing protection. Its known `app.whoosh.*` record services and removal markers are mapped to the Yap names and written to the new vault before caching. Existing Yap data wins; the previous consolidated vault remains untouched and is not reread once the new vault exists. Individual records from before consolidation retain explicit legacy aliases and migrate lazily through their existing Keychain protection. The first migration launch can still require approval for the old items; their access grants are not bypassed or silently transferred. A successful migration persists its record and marker before returning. Subsequent launches read only the consolidated item for migrated records. Missing setup does not create a new item, and a denied read is not remembered as missing credentials.

Token refresh and configuration saves use `SecItemUpdate` on the vault item, preserving its approved access controls. `SecItemAdd` is used only when the item does not exist. Failed writes do not replace cached credentials or remove a legacy copy. Migration leaves the protected legacy item intact; it is no longer read once its marker is durable. Explicit credential deletion first writes a durable removal marker in the active vault, then removes corresponding standalone legacy items. The prior consolidated vault is retained as migration history; active-vault markers and precedence prevent it from restoring an old token. If standalone legacy deletion fails, the durable removal still prevents restoration. That failure remains visible to the caller.

The vault creates no credential files, changes no Keychain ACL or certificate trust policy, and does not unlock Keychain or dismiss its approval dialogs. Google configuration bootstrap remains off the main actor, so a prompt for that bootstrap read does not prevent the app from drawing. This does not cover reads performed internally by the Zoom SDK.

## Separate Zoom SDK storage

The Meeting SDK owns an additional Keychain key, historically displayed by macOS as **Whoosh Safe Meeting Storage** before the rename. It is not one of the four application records and is not managed or cached by `CredentialVault`. An earlier host attempt waited for access to this key. The sampled main-thread stack passes through `ZMDB::Database::InitCryptoKey`, `zp_si_helper::GetDBEncKey`, `SecItemCopyMatching`, and `SecKeychainItemCopyContent`; see [the historical runtime sample](../../work/whoosh-post-permission-sample.txt). The macOS authorization dialog was independently observed. Earlier self-signed runs sometimes retained SDK access but later encountered an app-owned vault prompt. More recently, two successive changed Developer ID builds initialized, authenticated, and hosted without any further Keychain prompt. This establishes observed access through the SDK on this Mac; it neither inspects the SDK key's ACL nor preauthorizes every future SDK request. [Current live SDK log](../../work/live-developer-id-feature-verification.log).

Zoom staff historically explained that this storage protects the SDK's local database. In 2022, staff explicitly said the initialization prompt could not be hidden. That historical statement is consistent with the current SDK 7.1.5 public `ZoomSDKInitParams` header and API reference, which expose no Keychain opt-out, storage-provider hook, or asynchronous initialization option. It does not prove that Zoom has no internal alternative; none is documented in the checked public interfaces. [Zoom: storage purpose](https://devforum.zoom.us/t/sdk-initialization-requires-access-to-zoom-safe-meeting-storage-item-in-keychain/32852/8), [Zoom: optional-access discussion](https://devforum.zoom.us/t/can-keychain-access-during-initialization-be-made-optional/64712), [current initialization parameters](https://marketplacefront.zoom.us/sdk/meeting/macos/interface_zoom_s_d_k_init_params.html).

Zoom's current macOS guide describes initialization as synchronous, and its macOS PKCE guide requires Meeting SDK calls on the main thread. Consequently, Yap cannot safely fix this wait by moving SDK initialization into a detached task. The existing main-queue authentication and meeting watchdogs cannot run while initialization itself is blocked, and no public cancellable-init operation was found. Scheduling initialization after a UI update may let that update appear first, but cannot keep the app responsive during the synchronous SDK call. [Zoom: initialization](https://developers.zoom.us/docs/meeting-sdk/macos/get-started/), [Zoom: macOS SDK threading](https://developers.zoom.us/docs/meeting-sdk/macos/start-join-mtg-webinar/pkce/).

Normal authorization of this exact SDK-owned item and subsequent host/leave/relaunch/host checks are separate from the application vault. Some of those checks succeeded with the same signing identity across changed builds; the latest app-owned vault prompt shows that permanent approval cannot be inferred. A stable identity does not itself establish authorization for a previously unapproved item. Yap does not delete or recreate the SDK key, broaden its ACL, disable security interaction, or intercept the SDK's Keychain calls. If the prompt recurs with an unchanged designated requirement, preserve the observed prompt and SDK stack for Zoom support rather than treating the vault as the cause.

## Signing and the Keychain partition are separate from caching

Consolidation reduces the number of protected application items and repeated in-process reads. It cannot stabilize a signing identity or grant missing authorization. Apple's published Security implementation assigns recognized Developer ID/development code a `teamid:` partition and other signed code a `cdhash:` partition. The former self-signed certificate kept Yap's designated requirement stable, but that alone did not stabilize its build-specific partition. The current vault metadata now includes `teamid:VSVHNQP588`, and the two observed changed Developer ID builds retained account and SDK access. The app did not rewrite the item ACL or bypass normal authorization. [Apple Security source](https://github.com/apple-oss-distributions/Security/blob/main/securityd/src/clientid.cpp#L176-L274), [current metadata](../../work/whoosh-credential-acl-after-signed-update.json), [identity transition](Personal-Signing.md).

The read-only check of the exact vault item found an unlocked Keychain, disabled lock timeout/lock-on-sleep, `requirePassphrase=false`, and a partition matching the then-current self-signed binary's code hash. No password data was requested. These observations do not identify the cause of that particular prompt, and no mismatch should be inferred. [Metadata-only evidence](../../work/whoosh-credential-acl-before-developer-id.json). Developer ID is the stronger update route, not a promise of permanent preauthorization. Notarization was unperformed at that historical checkpoint; later pre-Yap packaging evidence is recorded in [Releases](Releases.md).

## Verification boundary

Nine vault fixture tests cover all four legacy records, one vault read on a subsequent launch, missing setup, denied access and retry, failed migration/update, preservation of other records, concurrent saves, deletion markers, and malformed vault data. They use injected in-memory storage and passed in the complete 247-test, 34-suite source checkpoint, which also includes five allowlisted preference-migration fixtures. [Current test log](../../outputs/Whoosh-Pure-Swift-Test-Log.txt). These fixtures do not exercise Zoom's internal Keychain item or grant live authorization. The two latest canonical Developer ID installs separately loaded real accounts and hosted with no Keychain or TCC prompt. Screen-capture permission had earlier been repaired through the user's normal System Settings flow; no direct ACL, trust, or TCC edits are part of this credential implementation. The final installed build also hosted without permission prompts and passed its selected-window sharing, minimized PiP, and Stop-to-main-onscreen checks. These media observations do not grant permissions; persistent physical foreground activation and full-display custom-panel exclusion remain unverified.
