## One secure item and one process cache

`WhooshCredentials.CredentialVault` consolidates the four records into one non-synchronizing generic-password item, `app.whoosh.credentials` / `personal-connections-v1`, accessible only while the device Keychain is unlocked. Each record retains its original service/account namespace. The shared vault serializes reads and updates across the calendar and Zoom actors, and caches successful reads for the running process. Ordinary view/status refreshes use that cache.

Existing records migrate lazily through their existing Keychain protection. The first migration launch can still require approval for the old items; their access grants are not bypassed or silently transferred. A successful migration persists its record and marker before returning. Subsequent launches read only the consolidated item for migrated records. Missing setup does not create a new item, and a denied read is not remembered as missing credentials.

Token refresh and configuration saves use `SecItemUpdate` on the vault item, preserving its approved access controls. `SecItemAdd` is used only when the item does not exist. Failed writes do not replace cached credentials or remove a legacy copy. Migration leaves the protected legacy item intact; it is no longer read once its marker is durable. Explicit credential deletion removes the legacy item as well and first writes a durable removal marker so an old token cannot be restored if legacy deletion fails. That failure remains visible to the caller.

The vault creates no credential files, changes no Keychain ACL or certificate trust policy, and does not unlock Keychain or dismiss its approval dialogs. Google configuration bootstrap remains off the main actor, so a prompt for that bootstrap read does not prevent the app from drawing. This does not cover reads performed internally by the Zoom SDK.

## Separate Zoom SDK storage

The Meeting SDK owns an additional Keychain key, displayed by macOS as **Whoosh Safe Meeting Storage**. It is not one of the four application records and is not managed or cached by `CredentialVault`. An earlier host attempt waited for access to this key. The sampled main-thread stack passes through `ZMDB::Database::InitCryptoKey`, `zp_si_helper::GetDBEncKey`, `SecItemCopyMatching`, and `SecKeychainItemCopyContent`; see [the historical runtime sample](../../work/whoosh-post-permission-sample.txt). The macOS authorization dialog was independently observed. Earlier self-signed runs sometimes retained SDK access but later encountered an app-owned vault prompt. More recently, two successive changed Developer ID builds initialized, authenticated, and hosted without any further Keychain prompt. This establishes observed access through the SDK on this Mac; it neither inspects the SDK key's ACL nor preauthorizes every future SDK request. [Current live SDK log](../../work/live-developer-id-feature-verification.log).

Zoom staff historically explained that this storage protects the SDK's local database. In 2022, staff explicitly said the initialization prompt could not be hidden. That historical statement is consistent with the current SDK 7.1.5 public `ZoomSDKInitParams` header and API reference, which expose no Keychain opt-out, storage-provider hook, or asynchronous initialization option. It does not prove that Zoom has no internal alternative; none is documented in the checked public interfaces. [Zoom: storage purpose](https://devforum.zoom.us/t/sdk-initialization-requires-access-to-zoom-safe-meeting-storage-item-in-keychain/32852/8), [Zoom: optional-access discussion](https://devforum.zoom.us/t/can-keychain-access-during-initialization-be-made-optional/64712), [current initialization parameters](https://marketplacefront.zoom.us/sdk/meeting/macos/interface_zoom_s_d_k_init_params.html).

Zoom's current macOS guide describes initialization as synchronous, and its macOS PKCE guide requires Meeting SDK calls on the main thread. Consequently, Whoosh cannot safely fix this wait by moving SDK initialization into a detached task. The existing main-queue authentication and meeting watchdogs cannot run while initialization itself is blocked, and no public cancellable-init operation was found. Scheduling initialization after a UI update may let that update appear first, but cannot keep the app responsive during the synchronous SDK call. [Zoom: initialization](https://developers.zoom.us/docs/meeting-sdk/macos/get-started/), [Zoom: macOS SDK threading](https://developers.zoom.us/docs/meeting-sdk/macos/start-join-mtg-webinar/pkce/).

Normal authorization of this exact SDK-owned item and subsequent host/leave/relaunch/host checks are separate from the application vault. Some of those checks succeeded with the same signing identity across changed builds; the latest app-owned vault prompt shows that permanent approval cannot be inferred. A stable identity does not itself establish authorization for a previously unapproved item. Whoosh does not delete or recreate the SDK key, broaden its ACL, disable security interaction, or intercept the SDK's Keychain calls. If the prompt recurs with an unchanged designated requirement, preserve the observed prompt and SDK stack for Zoom support rather than treating the vault as the cause.

## Signing and the Keychain partition are separate from caching

Consolidation reduces the number of protected application items and repeated in-process reads. It cannot stabilize a signing identity or grant missing authorization. Apple's published Security implementation assigns recognized Developer ID/development code a `teamid:` partition and other signed code a `cdhash:` partition. The former self-signed certificate kept Whoosh's designated requirement stable, but that alone did not stabilize its build-specific partition. The current vault metadata now includes `teamid:VSVHNQP588`, and the two observed changed Developer ID builds retained account and SDK access. The app did not rewrite the item ACL or bypass normal authorization. [Apple Security source](https://github.com/apple-oss-distributions/Security/blob/main/securityd/src/clientid.cpp#L176-L274), [current metadata](../../work/whoosh-credential-acl-after-signed-update.json), [identity transition](Personal-Signing.md).

The read-only check of the exact vault item found an unlocked Keychain, disabled lock timeout/lock-on-sleep, `requirePassphrase=false`, and a partition matching the then-current self-signed binary's code hash. No password data was requested. These observations do not identify the cause of that particular prompt, and no mismatch should be inferred. [Metadata-only evidence](../../work/whoosh-credential-acl-before-developer-id.json). Developer ID is the stronger update route, not a promise of permanent preauthorization. Notarization remains separate and unperformed.
