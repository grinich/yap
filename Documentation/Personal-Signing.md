## Why use Developer ID

A stable designated requirement is only part of Keychain identity. Apple's published `securityd` implementation assigns recognized Developer ID/development code a `teamid:` partition derived from the Apple-issued certificate; other signed code, including the former self-signed app, falls back to `cdhash:`. A self-signed build can therefore keep the same DR while its Keychain partition changes with its code hash. This is the rationale for moving Whoosh to the existing Apple-issued Team ID, not proof that the last prompt was caused by a partition mismatch. [Apple Security source, `partitionIdForProcess`](https://github.com/apple-oss-distributions/Security/blob/main/securityd/src/clientid.cpp#L176-L274), [Apple: code-signing requirements](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements).

The exact-item, metadata-only check found the Keychain unlocked, lock-on-sleep and lock timeout disabled, `requirePassphrase=false`, and a `cdhash:` partition matching the current self-signed executable. The check did not request password data, change item access controls, or modify trust. These facts leave the specific recurrence cause unresolved. [Read-only metadata](../../work/whoosh-credential-acl-before-developer-id.json), [historical blocked-read sample](../../work/whoosh-final-init-sample.txt).

Developer ID signing does not grant access to an existing protected item or silently migrate TCC permission. The first new-identity launch did wait in the background vault read while metadata still contained the former `cdhash:` partition; that is historical migration evidence. Normal authorization subsequently cleared this boundary. Current metadata shows `teamid:VSVHNQP588`, and account loading, SDK initialization/authentication, and own hosting succeeded across two changed Developer ID builds without further Keychain or TCC prompts. No direct ACL rewrite, ad-hoc workaround, trust change, or authorization bypass was used.
