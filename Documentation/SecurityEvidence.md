## CodeQL configuration and coverage

The Swift job selects the repository's Xcode 26.6 toolchain (Swift 6.3.3), initializes CodeQL, then performs a fresh manual arm64 build of the `Yap` product. CodeQL 2.26.2 explicitly added Swift 6.3.3 support. The workflow uses action v4 with current tools so it does not rely on an older bundled compiler extractor. [Exact compiler support](https://codeql.github.com/docs/codeql-overview/codeql-changelog/codeql-cli-2.26.2/), [manual Swift build guidance](https://docs.github.com/en/code-security/reference/code-scanning/codeql/build-options-for-compiled-languages)

JavaScript/TypeScript analysis uses the no-build mode. GitHub supports CodeQL scanning in public repositories; the workflow uploads language-specific results to the repository's code-scanning view. Keep the emitted CodeQL version and analysis logs with the run evidence. [Workflow options](https://docs.github.com/en/code-security/reference/code-scanning/workflow-configuration-options)

Coverage is limited to what each extractor analyzes. The public Swift build intentionally omits the proprietary Zoom SDK and the conditional SDK bridge path. CodeQL does not support Objective-C/Objective-C++, so the native bridge is not covered by this workflow. Vendor binaries, Apple/Zoom internal behavior, Cloudflare's platform, complete framework-specific behavior, and deployed configuration are not independently assessed by these scans. Manual review and actual-SDK tests remain necessary. [Supported languages and frameworks](https://codeql.github.com/docs/codeql-overview/supported-languages-and-frameworks/)

## Production service acceptance

The managed service at `https://meeting-auth.mgrinich.workers.dev` now runs API-only Cloudflare deployment `23757fca-b323-4f65-a8ce-42255449c072`; health returns 200 and `/terms` returns 404. Public documentation and Terms use GitHub. The same authentication logic, including service fix [`9d4e1dd`](https://github.com/grinich/yap/commit/9d4e1dd), passed a live production browser PKCE check at this host on preceding deployment `31a76568-0191-4f73-a3e7-d530fbc52966`. The check passed consent and the loopback callback, token exchange with all three required scopes, one bounded recordings-list page, and an SDK-signature response. Credentials stayed in the test process memory; this check did not write Keychain credentials, initialize the native SDK, exercise the app GUI, or test token refresh or revocation.

The earlier OAuth error **4700** was resolved by regenerating the production Beta authorization URL. A subsequent service failure was reproduced in the actual local Workers runtime: `redirect: "error"` was unsupported. The fix uses `redirect: "manual"` and explicitly rejects upstream 3xx responses. **24 service tests** and an actual local `workerd` before/after regression check passed. This current service validation is separate from the release baseline of 23 service tests.

The three returned scopes were `user:read:zak`, `meeting:write:meeting` and `cloud_recording:read:list_user_recordings`. No credential values or private recordings are included in this evidence. The successful signature response does not establish native SDK authentication, joining or hosting a meeting. Fresh-Mac installation, native account integration, refresh/revocation, and the remaining recording playback/uninstall acceptance checks are still required.
