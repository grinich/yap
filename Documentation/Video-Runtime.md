## Cause and correction

The previous live run at 09:54:11 reported two `ZoomSDKVideoSubscribe_Fail_TooFrequentCall` failures (reason **7**) for one remote video. Its show/subscribe calls returned synchronous success, but incoming statistics remained zero and the view stayed black. Reason 7 is rate limiting; it is not the gallery-capacity error.

Yap had been binding the element's `userid` and immediately calling `subscribeVideo:YES` again. Zoom's custom-view binding already initiates the subscription. The corrected initial path attaches and sizes the view, shows it, and binds the user once. It does not duplicate that subscription request. Repeated camera-off callbacks also avoid duplicate unsubscribe calls. This follows the [official custom UI lifecycle](https://developers.zoom.us/docs/meeting-sdk/macos/custom-ui/custom-ui-feature/) and Zoom staff's clarification that an explicit initial subscribe call is [not mandatory](https://devforum.zoom.us/t/inconsistent-black-screen-video-for-participants-on-join/62975/6).

An actual reason-7 callback now schedules one retry after 1.5 seconds, then 3 seconds, then 6 seconds if needed, with a maximum of three retries. Duplicate callbacks share the pending retry. Session, element, and retry-token checks discard stale work after camera changes, paging, or teardown. This retry logic is present, but the successful initial live binding above did not need a retry. Capacity guidance is reserved for the SDK's actual capacity failures.

The AppKit host rejects unattached, hidden, nonfinite, and zero-sized geometry. It coalesces layout work, avoids identical resizes, and forwards valid changes to Zoom's renderer. Those lifecycle cases pass the standalone native fixture in `Tests/YapZoomBridgeTests/RenderHostLifecycleTests.m`; that fixture is separate from the live media evidence.

## Gallery and visibility review after the live release checkpoint

A subsequent source review found that a tile created in a gallery larger than 25 people received a fixed 90p cap. Cached elements kept that cap when their participant moved into a large focus tile or a smaller gallery. The creation-only cap is now removed: each element receives its current renderer geometry, and Zoom chooses the incoming quality. Yap does not add a resolution-setting call that could trigger another subscription. This correction does not establish any live large-gallery capacity or guarantee a particular received resolution.

The render host now checks AppKit's `visibleRect` as well as the containing window's visibility, minimization, and occlusion state. It observes the actual ancestor hierarchy's bounds/frame changes instead of assuming SwiftUI uses a particular scroll-view implementation. Entirely clipped tiles suspend their subscription; partially visible tiles remain eligible. Window, hide, and scroll updates are coalesced, unchanged geometry is ignored, and the existing delayed retry guards prevent stale or hidden elements from resubscribing. [Apple's visible rectangle contract](https://developer.apple.com/documentation/appkit/nsview/visiblerect).

## Later outgoing window-sharing checkpoint

That live run exposed a separate control-state bug: Yap dismissed its chooser but did not show the active-sharing banner or Stop/Switch controls. Source review found an unnecessary owner-ID equality check before publishing `ZoomSDKShareStatus_SelfBegin`. The SDK defines that status as the current user beginning sharing, and the bundled official sample handles it directly. The correction treats SelfBegin/SelfEnd as authoritative local state while requiring a known matching owner for the generic Resume status. It adds diagnostics containing SDK codes/status and metadata-presence booleans, never source titles or identifiers.

A further lifecycle check found that the sharing delegate was installed during authentication, before the AS controller exists. Zoom creates that controller only after meeting admission; assigning its delegate earlier can silently do nothing. The corrected bridge reacquires and installs the sharing delegate on each confirmed InMeeting callback, before emitting the joined state or refreshing shares. Its safe diagnostic reports only whether the controller exists and the delegate was installed. Teardown still clears the delegate safely when available. This follows the current SDK7.1.5 sample and [Zoom's explicit lifecycle explanation, post36](https://devforum.zoom.us/t/zoomsdkerror-4-on-ui-functions/38576?page=2).

The mapping passes a Foundation-only fixture compiled with the actual SDK7.1.5 enum header; the full native bridge also passes its SDK syntax check, including the later delegate correction. ## Focus handoff regression and bounded correction

Returning to the gallery remained blank; the remote camera off/on cycle later restored gallery frames. Source review identified an ownership race: the outgoing gallery representable could reclaim the cached SDK view after the incoming focus representable had adopted it, then remove it during dismantle.

The first mount-order correction passed isolated handoff tests but the next real app run did not attach gallery video. The final `NativeVideoHost` claims a weak ownership lease only after real window attachment and nonzero layout; an allocation or zero-size probe cannot displace a usable renderer. Actual window detachment releases attachment priority, while temporary zero-size layout does not renew it. The host explicitly forwards layout/frame/bounds changes, and `NativeRendererContainer.sizeThatFits` honors the parent tile's proposal. Explicit participant identity also prevents reusing an older A focus host for B's renderer. SDK subscription and received-sharing code are unchanged.
