## Native PKCE and code-only HTTPS relay

1. The Mac generates three independent random values: the OAuth PKCE verifier, a handoff verifier, and the native sign-in nonce. It keeps the pending attempt and both verifiers in memory. It sends only the two S256 challenges, the nonce, and the public client ID to `/v1/oauth/session` on its fixed Yap service origin.
2. The service returns a Zoom authorization URL containing the configured public client ID, S256 challenge, fixed HTTPS callback, and authenticated encrypted state. The state binds the client, callback, nonce, challenges, and an expiry of at most 180 seconds. Yap validates the authorization URL before opening the browser. The OAuth PKCE verifier never goes to this service.
3. Zoom redirects the browser to the branded HTTPS callback with an authorization code. The service validates state and puts **only that code** into a new, purpose-separated encrypted handoff; it does not exchange the code. Invalid or expired callbacks return a restart page. Denied consent offers a return to Yap without tokens or a successful-connection claim.
4. The browser completion page offers **Open Yap**, carrying the native nonce and encrypted code handoff at `yap://oauth/zoom`. This custom URL contains no plaintext OAuth code, verifier, access token, or refresh token. It is the return to the native app, not the registered Zoom callback.
5. Yap accepts the callback only for its pending nonce, consumes that pending response once, and redeems the handoff at `/v1/oauth/handoff` with the separate handoff verifier. The response contains exactly `code`, `client_id`, and `redirect_uri`. The Mac checks the client and callback against its bundled configuration and rejects the former token-returning response format.
6. The Mac posts the code, original OAuth PKCE verifier, public client ID, and exact redirect URI directly to `https://zoom.us/oauth/token`. There is no client secret or Basic Authorization header. Yap validates own-user ZAK access and saves the returned access/refresh tokens in Keychain before reporting a successful connection. Refresh also runs directly between the Mac and Zoom.
7. The native Meeting SDK receives the public client ID in `ZoomSDKAuthContext.publicAppKey`. Yap waits for successful asynchronous SDK authentication. Joining or hosting additionally requires the signed-in user's fresh ZAK and the meeting's applicable permissions. Camera settings can initialize the public SDK without fetching ZAK or joining a meeting; SDK authorization alone does not start capture.

The managed flow opens no local HTTP OAuth listener. Its state and code handoff use versioned, separate-purpose AES-GCM envelopes, each valid for at most 180 seconds. The service retains a server-only relay encryption secret, but does not need the Zoom OAuth/SDK client secret. It keeps no persistent user, OAuth-token, or session database. Original Zoom access/refresh tokens never pass through the relay. Token-bearing native HTTP requests refuse redirects, use an ephemeral session, and omit token values and provider response bodies from user-facing errors. [Native relay client](../Sources/YapMeetings/ZoomManagedOAuth.swift), [native token exchange](../Sources/YapMeetings/ZoomAccountClient.swift), [service routes](../Services/zoom-auth/README.md), [Privacy](../PRIVACY.md).

The desktop nonce is consumed once, but the stateless relay does not store redemption records. A code handoff plus its separate handoff verifier can be redeemed again within its validity window; Zoom's authorization code can only be exchanged successfully once and still requires the native OAuth verifier. Do not describe the relay itself as enforcing single-use redemption. Encrypted state/handoffs and Zoom's callback query may remain in browser history; expiration does not erase that history. HTTPS, restrictive response headers, and the PKCE proof are separate protections.

All current Zoom flows request the user-level scopes `user:read:zak`, `meeting:write:meeting`, and `cloud_recording:read:list_user_recordings`. These authorize the signed-in user's SDK identity, explicit instant-meeting creation, and own-user cloud-recording library. SDK chat, sharing, and recording controls use meeting permissions rather than additional REST scopes. There are no separate Yap login credentials or app-owned user roles. Native public-client authorization does not remove Zoom's Marketplace review requirement for externally hosted meetings. [Meeting SDK authorization](https://developers.zoom.us/docs/meeting-sdk/auth/).

The `/connect` page offers **Connect Zoom in Yap**, opening `yap://connect/zoom`; Yap then starts sign-in or shows the existing connection settings. Validate this entry route, browser consent, branded callback, native return, denial/cancellation, wrong/expired state, direct refresh, and reauthorization against the final packaged candidate.

## Upgrade and historical authorization boundaries

The earlier `/v1/oauth/token` token proxy and `/v1/meeting-sdk/signature` signer are retired with `410 update_required`. Old session requests that send a `code_verifier` to the service also require an update. Known legacy `workers.dev` authorization routes no longer exchange or refresh credentials; their old browser callbacks direct users to restart sign-in in the updated app. They must not silently forward old installers into the new public-client flow.

Updating from a confidential-client or earlier proxied connection requires **Sign in to Zoom** again. The 0.1.8 app accepts saved managed tokens only when their public client ID matches and they carry the native-PKCE provenance marker written by the new exchange. It does not relabel, refresh, or reuse earlier managed credentials under the new client, even if an older record has the same public client ID. A successful fresh sign-in replaces the Zoom record; disconnect removes it. Google credentials are preserved. [Credential storage](Credential-Storage.md).

**Historical September 14 version boundary:** released **Yap 0.1.6 (build 7)** used public-client OAuth with a temporary local HTTP callback and service-assisted token exchange/SDK signing. The subsequent HTTPS review candidates used the confidential Production Client ID, first with the `workers.dev` callback and later the Yap domain. Those immutable installers do not acquire the 0.1.8 native-PKCE architecture through a website update. ## Legacy personal developer setup

This owner-only configuration is retained for development. It is not required for the official managed app and is not the setup for the upcoming production HTTPS callback.

There are separate layers: SDK application authentication, the human's Zoom identity, and permission to enter a particular meeting. Yap uses the human identity/ZAK path, including host access, rather than a bot identity. An SDK JWT alone does not provide a user's hosting authority. Meetings outside the developer account require the applicable Zoom app review and authorization even when Yap is only for personal use. Test an account-owned meeting first, then externally hosted meetings once authorized. [Authorization FAQ](https://developers.zoom.us/docs/meeting-sdk/obf-faq/).

### Personal public-client configuration

For this legacy personal path only, use the owner's user-managed General app with **Use Public Client OAuth**, register `http://127.0.0.1/callback`, and add `user:read:zak`, `meeting:write:meeting`, and `cloud_recording:read:list_user_recordings`. The meeting-write scope creates a meeting for the signed-in user on **Start new meeting**; the recording scope enables that user's library. No administrator scopes are requested. The legacy native PKCE flow uses an ephemeral loopback port with the registered host/path, a fresh state and S256 verifier. It separately uses the owner's SDK Client ID and Client Secret for local SDK signing. Do not configure the new confidential production client to use this HTTP loopback path. [Native OAuth](https://developers.zoom.us/docs/integrations/oauth/), [Meetings API](https://developers.zoom.us/docs/api/meetings/).

In Yap Settings, choose **Enter Zoom configuration…**, enter the regular **Client ID**, paste the **Client Secret** into its native secure field, and enter the **Public OAuth Client ID**. Save configuration writes directly to a non-synchronizing, unlocked-device-only Keychain item. The secret field clears immediately on Save and all fields clear on dismissal. Existing configuration can be replaced from its settings menu; replacement disconnects the saved Zoom authorization and requires sign-in again. Configuration changes are disabled during calls and connection mutations.

JSON import remains available. The schema below uses labels, not actual credentials; manual entry avoids creating an additional plaintext credential file.

```json
{
  "sdkClientID": "REGULAR_CLIENT_ID_FROM_ZOOM",
  "sdkClientSecret": "CLIENT_SECRET_FROM_ZOOM",
  "oauthPublicClientID": "PUBLIC_CLIENT_ID_FROM_ZOOM"
}
```

`ZoomAccountClient.configure(fromJSON:)` imports this configuration. In **personal mode**, `connect(openURL:)` opens the system browser, verifies the loopback response, exchanges the code directly with Zoom, validates ZAK access, and saves rotating OAuth credentials. `meetingCredentials()` obtains a fresh five-minute ZAK from `/v2/users/me/zak` immediately before joining and makes a one-hour native SDK JWT locally. `hostingCredentials(title:)` also creates an own-user instant meeting via `POST /v2/users/me/meetings` with `type: 1` and returns its numeric ID alongside fresh SDK credentials. `disconnect()` removes local OAuth credentials; `removeConfiguration()` also removes the imported developer settings. Disconnect does not claim to revoke Zoom's server-side app authorization. [Authenticated-user ZAK endpoint](https://developers.zoom.us/docs/api/users/), [native SDK JWT format](https://developers.zoom.us/docs/meeting-sdk/auth/), [Meetings API](https://developers.zoom.us/docs/api/meetings/).

The created room uses host and participant video off, mute upon entry, waiting room on, join before host off, and no personal meeting ID. Automatic recording, meeting summary, and AI Companion questions are explicitly off. Yap sends no invitations. The prepared room ID is reused across retries until the SDK confirms InMeeting; cancellation after a confirmed creation retains that ID. An uncertain creation result blocks another POST until an explicit reconnect, avoiding duplicate meetings. Missing creation permission produces a reconnect/setup error instead of widening authorization silently.

The **legacy loopback** callback displays a self-contained Yap completion page with the app icon, light/dark appearance, reduced-motion support, and an explicit **Open Yap** button. That legacy page clears the authorization query from the address bar. It does not claim the connection is complete before token exchange: Yap comes to the foreground only after the token exchange, ZAK check, and credential save succeed. Its button uses the parameter-free `yap://open` route, which only reveals the main window. These local callback pages load no external assets, prohibit caching, and use a nonce-based Content Security Policy. The upcoming managed HTTPS completion page and encrypted `yap://oauth/zoom` handoff are a separate implementation described above.

Token-bearing HTTP requests refuse redirects and use an ephemeral session. Error messages omit response bodies and token values. OAuth/token/meeting-creation unit tests use fixtures. Separately, real account authorization, ZAK retrieval, SDK host startup, and incoming camera video from an independent Zoom endpoint have been verified through Yap. ## Native bridge implementation contract

`ZoomMeetingDriver` implements the `MeetingDriver` boundary through the `YapZoomBridge` target. The app should construct it using `makeZoomMeetingDriver(accountClient:)` with the same actor used by its Zoom connection settings. `MeetingCoordinator` owns visible state and rejects callbacks tagged with a different session UUID. The driver must own the SDK instance, callback delegates, native video elements, and subscriptions for the whole session. SDK callbacks must be marshaled onto the main actor before calling `onEvent`; copy scalar values before crossing threads rather than sending SDK objects between actors.

The native boundary is Objective-C and compiles against the downloaded public SDK headers. The Swift wrapper receives copied, in-memory event payloads on the main actor. SDK logging remains disabled. Native consent sheets retain the SDK-provided text and require a person to act; Yap does not silently accept recording or archiving notices.
